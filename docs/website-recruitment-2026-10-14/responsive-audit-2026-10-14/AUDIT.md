# OnlyNail 官网响应式与折叠屏审查

审查日期：2026-10-14 至 2026-10-15
范围：首页首屏、小程序引导、邀请申请入口；桌面、常规手机、折叠屏外屏与展开态。
目标：确认美甲师能理解产品、体验小程序并顺利进入邀请申请，同时不因屏幕形态丢失内容或操作入口。

## 总体结论

当前官网已经达到可用且有一致性的移动优先基础：390px 常规手机和 344px 主流折叠屏外屏均无横向溢出，交互控件未发现低于 44px 的情况；768px 展开态能够形成稳定双栏。视觉层级、收费口径、小程序与申请关系也较清楚。

仍有明确优化空间，且目前不能称为“已针对折叠屏优化”：280px 超窄外屏会因为根节点 `min-width: 320px` 产生横向溢出；代码没有铰链或双视口分区处理；固定底部申请条在移动端从首屏开始一直占据空间。折叠屏当前属于“宽度响应可用”，还不是“形态感知适配”。

## 审查步骤

1. **桌面首页，1440×1000：良好**
   双栏结构清楚，产品流程示意与申请动作并列。顶部留白较多，主价值信息进入视野偏晚；缺少真实作品或真实产品截图，视觉可信度主要依赖文字和示意界面。

2. **常规手机首页，390×844：良好**
   标题、正文和双按钮都能自然换行；没有横向滚动，控件达到触控尺寸。固定申请条与首屏内申请按钮重复，持续占用约一行内容高度。

3. **折叠屏主流外屏，344×882：良好**
   页面正常单列，两个主动作改为上下排列，演示卡可读，未发现横向溢出或过小控件。此宽度可作为当前外屏支持下限的主要验收档位。

4. **折叠屏超窄外屏，280×653：需修复**
   实际文档宽度为 320px，超过 280px 视口；菜单、正文、按钮和演示区域右侧被裁切。根因是 `body, #root { min-width: 320px; }`。这也会影响高倍放大后的响应式回流。

5. **折叠屏展开态，768×1024：良好，有限制**
   首页保持双栏，内容没有横向溢出，视觉平衡尚可。当前布局只根据总宽度判断，没有识别铰链或两个可视分区；在双屏设备或浏览器暴露 viewport segments 时，内容和固定操作条可能跨过铰链。

6. **小程序引导，390×844：可用，可精简**
   扫码、公开体验和获邀开通的关系解释清楚。手机用户无法直接扫描当前屏幕上的二维码，而二维码卡位于更下方；移动端应优先显示“微信搜索、复制名称、保存图片”，二维码作为桌面主路径。

7. **移动端申请页，390×844：可用**
   字段标签清晰，输入框高度充足，16px 输入字号可避免 iOS 自动放大。首屏连续展示五个必填项，但看不到提交动作或填写进度，容易让表单显得比实际更长。

## 已确认的优点

- 中性色系统统一，主次按钮和状态说明容易区分。
- 首页在 344px、390px、768px、1440px 都能形成明确层级。
- 移动端导航收起，主要按钮触控区域达到 44px。
- 固定申请条已经包含底部安全区变量；页面也尊重 `prefers-reduced-motion`。
- 小程序流程示意明确标注为示例数据，没有冒充真实客户案例。
- 申请页使用原生表单语义、可见标签和 16px 输入字号。

## 主要问题与优先级

### P0：消除 320px 最小宽度造成的裁切

移除 `body` 和 `#root` 的强制 `min-width: 320px`，允许布局收缩到 280px；为 280–319px 增加更紧凑的页面边距、按钮文案与演示标签处理。完成后重新检查首页、二维码弹窗、菜单和申请表单。

### P1：增加折叠屏形态感知

使用渐进增强方式检测多 viewport segments，在支持的浏览器中把主内容、二维码卡和固定申请条限制在单一可视分区，或为铰链预留中间空隙。普通浏览器继续使用现有断点，避免把实验性 API 作为唯一布局基础。

### P1：补齐安全区声明

`index.html` 的 viewport meta 目前没有 `viewport-fit=cover`。固定底部申请条虽然使用 `safe-area-inset-bottom`，仍应补齐该声明，并在刘海屏、圆角屏和横屏下实测。

### P1：降低移动端固定 CTA 的干扰

首屏已有申请按钮，底部固定条无需从页面加载时立即出现。建议在首屏按钮离开视口后再显示，并在菜单、二维码弹窗或软键盘出现时隐藏，减少遮挡和重复。

### P2：调整移动端小程序引导

桌面保留二维码；移动端把“微信搜索 OnlyNail”“复制名称”“保存小程序码”放在前面，二维码缩小或折叠。这样更符合用户在同一台手机上浏览官网的真实操作方式。

### P2：增加真实视觉证据

当前示意界面清楚但偏抽象。获得授权后，可在首屏之后加入 1–2 张当前发布版小程序截图或真实作品/工作室案例。真实作品颜色属于内容，不违反官网中性色规范。

### P2：降低申请表单的感知成本

在表单卡片顶部说明“5 项必填，补充介绍可选”，或把必填项分成联系方式与服务方式两个小组。无需增加步骤页，保持一次完成即可。

## 无障碍风险与验证边界

- 280px 下的水平滚动是明确的响应式回流风险，也可能影响 200% 或更高页面缩放。
- 390px 与 344px 下未发现低于 44px 的可见按钮或链接；这不等同于所有动态状态均已验证。
- 截图可以确认视觉层级和可见性，不能确认屏幕阅读器播报、完整键盘顺序、浏览器缩放、虚拟键盘、真实刘海安全区或真实铰链遮挡。
- 铰链适配需要在支持 viewport segments 的模拟器或真机上补测；普通视口缩放无法模拟物理铰链。

## 建议实施顺序

1. 修复小于 320px 的回流并补 `viewport-fit=cover`。
2. 调整固定申请条的出现时机和弹层/键盘状态。
3. 优化移动端小程序引导动作。
4. 增加折叠屏 segment 渐进增强和真机验收。
5. 获得授权后补真实截图或案例。
