# OnlyNail 招募官网开发计划与任务

日期：2026-10-14 ｜依据：[可行性报告](REPORT.md)｜状态：待排期，未实施

## 1. 范围与成功标准

用户已于 2026-10-14 确认：**小范围邀请入驻，先积累案例。** 首期围绕人工审核、协助开通、真实使用和案例沉淀组织任务。5–8 位试用者仍是建议样本数量，并非用户确认的招募配额。

目标是让符合画像的美甲师看懂产品、提交有效申请、被审核并完成小程序开通。开发围绕 `website/`、必要的 `backend/` 和 `admin-frontend/` 改动；小程序只在核实激活/归因确有缺口时另列任务，不顺带重做其他端。

成功标准：

- 官网每项公开承诺有可用能力或确认过的运营政策支持，当前发布版演示与实际一致。
- 上门、到店、两者均可三种申请，在审批后得到正确的账号配置。
- 申请→审核→Key 交付→小程序激活→预约基础设置在隔离环境可完整验证，状态可区分。
- 申请失败不丢失输入，重试不重复创建；咨询渠道真实可达。
- 320–1440px 无内容截切，核心控件至少 44px，安全区、键盘及弹层可用。
- 能区分流量/申请/审核/激活，来源可以追踪，未把扫码等同于注册或开通。

## 2. 阶段与工作量

按熟悉项目的开发团队估算；人日为实际工作量，日历时间受人员分工、素材和政策确认影响。以下区间已包含本阶段必要验证，不重复叠加整套回归。

| 阶段 | 工作内容 | 预计人日 | 退出条件 |
|---|---|---:|---|
| M0 定位与证据确认 | 范围、政策、素材及运行条件 | 2–3 | 明确招募阶段、当前承诺和发布版能力 |
| M1 招募闭环修复 | 申请契约、防重复、审核交付、真实联系 | 6–9 | 隔离环境端到端开通通过 |
| M2 官网内容与手机体验 | 首页重组、表单、演示、FAQ、信任与基础分享 | 6–9 | 文案与移动交互验收通过 |
| M3 归因、发布验收与试招募 | 最小记录、渠道核验、回归、运营演练 | 5–7 | 阻断问题清零，可以邀请首批用户 |
| **合计** | **首期可交付范围** | **19–28** | **建议预留约 4–6 周，排期后再承诺日期** |

M0 → M1/M2 → M3。M1 与 M2 只有在字段和政策已定后才可由不同人员并行；这不是授权自动创建并行代理或修改业务代码。后续 P2 不计入首期。

## 3. 任务清单

所有任务当前为“未开始”。P0 指阻断招募真实性或开通闭环；P1 指首期转化与质量要求；P2 指有真实需求再做。

### M0：明确可以招募谁、承诺什么

**W01｜P0｜招募与费用口径冻结**

- 责任：产品负责人＋运营。依赖：无。
- 已确认：小范围邀请入驻，先积累案例，无需重复确认招募阶段。
- 交付：细化邀请对象与运营承接能力；当前费用、试用及退出条件；审核时效；品牌名称说明。
- 验收：每个公开承诺有负责人确认；没有未决价格被写成确定事实；主 CTA 与阶段相符。
- 对应：F04、F07，报告第 10 节。

**W02｜P0｜发布版能力与招募可用性核对**

- 责任：后端＋小程序开发。依赖：W01。
- 范围：只读核对生产发布版本、`MINIPROGRAM_LAUNCH_MODE`、目标账号访问边界及激活方式；在测试环境复现新美甲师流程。
- 验收：列出“本地有／已发布／受配置限制”的差异；两个测试美甲师分别可访问本人数据，不能访问对方私有数据；不因招募而自动关闭现有限制。
- 对应：F02。若仍限制单工作室，发布只能采用意向登记或保持受控邀请。

**W03｜P1｜当前产品素材与案例清单**

- 责任：设计＋运营＋小程序开发。依赖：W02。
- 交付：新版主页、预约、容量设置、客户记录、经营数据脱敏截图；至少一套可连贯讲解的操作场景；作品和评价授权记录。
- 验收：截图标注来源版本和角色；不包含客户手机号、地址或真实经营敏感数字；案例没有虚构增长指标；没有真实案例时明确为演示。
- 对应：F06、F10。

### M1：先保证申请进来的人能真正使用

**W04｜P0｜统一服务模式契约**

- 责任：前后端。依赖：W01。
- 文件：`website/src/pages/ArtistApplicationPage.tsx`、`website/src/services/api.ts`、`backend/src/artist-applications/dto/create-artist-application.dto.ts`、`artist-applications.service.ts`、管理后台 `ArtistApplications.tsx`。
- 实施：将自由文本改为 home/shop/both；如允许未选择，在后台补全后才能审批。只读盘点历史值，制定映射，不猜测其他中文填写意图。
- 验收：三种模式完整申请/审批测试分别得到 true/false、false/true、true/true；非法值返回字段错误；缺省不会创建双关闭账号；历史未知值保留人工处理出口。
- 对应：F01。

**W05｜P0｜服务端校验、重复申请与公开响应**

- 责任：后端＋官网。依赖：W04。
- 实施：手机号格式、trim、字段长度；服务端原子去重或幂等策略；拒绝后重申规则；核查全局限流，按实际不足补防护。移除仅凭手机号公开区分 pending/approved 的必要性，公众得到一致可行动结果。
- 验收：空白、非法手机号、超长内容不写库；并发重复只有一条有效待处理申请；网络超时后重试可恢复；已拒绝可按规则重申；公开接口不暴露他人申请或激活状态；错误不含内部数据。
- 对应：F12。前端按钮禁用不替代后端控制。

**W06｜P0｜审批到激活的交付清单**

- 责任：后台＋后端＋运营。依赖：W02、W04、W05。
- 文件：`admin-frontend/src/pages/ArtistApplications.tsx`、`Technicians.tsx`、申请服务、technicians 服务；小程序现有激活流程用于验收。
- 实施：申请关联账号；审批后能进入生成/复用 16 位激活 Key 的既有流程；显示待交付/已联系/已激活的事实或最小记录，明确人工发送责任。优先复用接口，不另造账号体系。
- 验收：一个申请只关联一个账号；重复审批/生成不创建多个有效身份；Key 一次使用、权限与日志脱敏符合既有机制；运营能定位未交付申请；成功激活后能看到正确账号及服务模式；8 位客户邀请码不冒充激活 Key。
- 对应：F02。

**W07｜P0｜替换模拟联系表单**

- 责任：官网＋运营。依赖：W01。
- 文件：`website/src/pages/ContactPage.tsx`，关联文案。
- 实施：首期使用真实可达的运营联系渠道及服务时段；只有确有必要且有人处理时才接收留言 API。
- 验收：不再出现定时器模拟“发送成功”；手机可以复制/查看联系方式；运营完成一次实际收件验证；未配置联系渠道时不展示无效入口。
- 对应：F03。

- 验收：新访客能准确复述“给谁、做什么、怎么开始”；390px 不再标题孤字及正文截切；320/375/430/768/1440px 同样可读；首屏和结尾均可直接申请；普通卖点不彩色分组。

- 验收：不关注公众号也能提交；可选字段为空可提交；错误就近可见；网络错误重试不丢数据/不重复提交；成功页仅在服务器确认后展示；审核通过与已激活不混淆。

- 验收：桌面扫码、微信内、Safari、Android 浏览器分别有明确路径及降级；目标正确；链接失效可恢复；用户不会误进入真实工作室下测试订单；无法验证直达时仍能在官网看演示。

**W11｜P1｜费用、FAQ、隐私和案例可信度**

### M3：验证招募质量并形成可回溯的发布

**W13｜P1｜最小招募归因**

- 责任：后端＋官网＋后台。依赖：W05、W06、W09。
- 实施：申请保存白名单来源/活动代码，关联审核结果与 technicianId。后台可查看或导出申请到激活的记录，先复用已有列表，不建立新 BI 平台。
- 验收：带来源与无来源申请都可处理；刷新/重试不重复计为新申请；后台事实可追溯；来源字符串长度受限；统计与日志不包含微信号、手机号或激活 Key。
- 对应：F11。

**W14｜P1｜隔离环境端到端验收**

- 责任：测试＋全栈开发＋运营。依赖：W06–W13。
- 准备：明确测试后端地址与测试账户，禁止沿用目前指向生产 API 的本地代理提交虚构申请。
- 覆盖：三种服务模式、重复申请、拒绝重申、异常网络、审批/交付/激活、首次配置服务/营业时间/作品、权限隔离、移动端实际浏览器。
- 验收：用户能从官网进入并完成开通；每个状态运营能解释和处理；严重缺陷清零；受平台限制的场景有真实兜底；记录版本和截图。
- 运行：官网相关测试与类型检查/构建；新增申请/审批契约测试；后台按实际改动构建；小程序仅跑受影响的激活/预约相关测试。不扩大到 iOS、Flutter 或历史客户 Web。

**W15｜P1｜发布包、回滚与试招募交接**

- 责任：开发＋运维＋运营。依赖：W14。
- 实施：明确官网是本次**独立发布项**，不能夹带在普通 ECS 后端/后台更新里；仅在收到实施/发布授权后推进。ECS 部署遵循本地或 CI 构建、服务器资源检查/备份、串行更新及保留回滚版。
- 验收：官网静态资源、后端契约与后台版本相容；新增迁移可安全部署；能回滚到上个官网版本且 API 保持兼容；若修改小程序，上传/提审/发布另记，不称 ECS 更新即小程序更新。
- 运营：建议邀请首批 5–8 位目标美甲师、提供开通清单、记录每次协助和失败原因；没有完成开通者必须有后续处理责任人。
- 案例验收：试招募复盘时至少形成 1 份经授权的真实使用案例，包含工作方式、实际使用功能、遇到的问题与反馈；有经营效果数据时注明周期与来源，没有数据时不编造提升幅度。该项为试招募后的运营产出，不阻断首批邀请前的技术发布。

## 5. 核心验收用例

| 用例 | 预期结果 |
|---|---|
| 到店／上门／两者申请审批 | 对应服务能力配置正确 |
| 未选服务模式 | 按约定明确补全，不产生不可服务账号 |
| 手机号为空、空白、格式错误、超长文本 | 字段错误，后端拒绝写入 |
| 同一申请并发提交或超时重试 | 只有一个有效处理对象，不重复开通 |
| 已拒绝者重新申请 | 按明确业务规则重新进入审核 |
| 已通过但尚未激活 | 文案与后台状态不称“已开通” |
| Key 已使用、错误、交付失败 | 明确错误与补救入口，不暴露他人账户 |
| 两位美甲师分别登录 | 仅可管理本人客户/预约/作品等私有数据 |
| 不关注公众号 | 申请正常提交，不把自报关注当通知可达证明 |
| 作品接口失败、分享链接失败 | 仍可看核心演示、申请及获取真实帮助 |
| 联系入口 | 实际到达运营，不模拟成功 |
| 官网与小程序不同发布版本 | 宣传仅覆盖实际可用能力，差异有记录 |

## 6. 研发启动顺序

先完成 W01/W02，再定字段契约和素材，进入 W04–W07。随后交付 W08–W12，最后实施 W13–W15。任何任务增加范围时更新估算和验收，不把“招募官网”扩展成全产品改造。

本轮仅完成报告、计划和证据整理；上述任务均未标为已开发。
