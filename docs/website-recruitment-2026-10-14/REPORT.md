# OnlyNail 官网招募可行性与设计需求报告

日期：2026-10-14 ｜对象：微信小程序产品与本地官网最新工作区｜性质：调研、评估与开发规划，非上线验收

## 1. 决策结论

**建议在现有 `website/` 上迭代为美甲师招募官网，先开展小范围邀请入驻；技术基础足够，全面推广仍有明确前置条件。** 官网应负责解释价值、展示真实产品、消除顾虑、收集有效申请，并把申请人交付到可使用的小程序账号。只重新美化首页不能完成这个目标。

推荐定位：**给独立美甲师的微信预约与客户经营工具。** 核心表达是“让客户更容易预约，让你更清楚地管理档期、服务记录和老客”，不承诺平台派单或保证增收。官网招募的是产品使用者，不是招聘雇员，也不是向消费者销售美甲服务。

当前最值得先解决的五件事：

1. 修复申请服务模式与后台创建账号的字段契约。
2. 接通申请审核、激活 Key 发放与首次使用的运营链路。
3. 取消以自行勾选“已关注公众号”作为申请阻断条件；公众号改为辅助触达。
4. 下线联系表单的模拟成功，提供真实有效的联系入口。
5. 用新版小程序真实场景替换旧预览图，补齐费用、开通方式和使用边界。

### 已确认的招募阶段（用户确认，2026-10-14）

用户本次目标为招募美甲师，优先于历史路线图。仓库 10 月 9 日路线图及 10 月 13 日容量 PRD 仍描述“先服务一个工作室”；而当前代码已默认采用多租户模式，仅在显式配置时限制单美甲师。因此不能以旧文档认定新美甲师不可加入，也不能仅凭代码默认值认定线上已开放。

用户已确认：**小范围邀请入驻，先积累案例。** 官网首期采用邀请制招募，主行动建议为“申请邀请入驻”，说明人工审核与开通支持；不承诺提交后立即开放。首期成果应包括可用账号、真实使用反馈和经授权的工作室案例。已确认邀请体验期免费、后续收费另行通知，并由 NailBook 微信公众号接收入驻咨询；客服人力与生产开关仍需在招募前确认；扩大招募另行依据案例和使用结果决策。

## 2. 范围、方法与证据边界

- 审查基线：Git HEAD `0cf377ae` **加本地所有已有未提交修改**。用户已在其他地方更新，因此以实际工作区文件为准，不回退到提交版本。
- 官网主体：`website/`。`docker-compose.yml` 指向它，主域 Nginx 转发到 website 服务。`start-all.sh` 仍启动 `landing-frontend/`，属于入口混用风险，不应双线改版。
- 核实对象：`client-wxapp/` 的客户端、美甲师端，`backend/` 的申请、账号、预约、经营与分享服务，`admin-frontend/` 的申请审核。
- 浏览器审查：本地官网首页、扫码体验、申请表单、FAQ、联系页；移动视口 390×844、桌面 1440×960。截图与逐步记录见 [EVIDENCE.md](EVIDENCE.md)。
- 桌面调研：Fresha、GlossGenius、有赞官方产品页面，检索日期 2026-10-14。仅用于信息架构与产品定位对照，不将官方营销效果数字视为独立证据。
- 没有真实美甲师访谈、流量/留资数据、投放成本或付费意愿数据。下面画像与转化判断是待验证假设，不能证明市场规模、收益或增长幅度。
- 未登录生产管理后台、未提交真实入驻申请、未发送微信消息。官网开发代理指向生产 API，因此没有执行写入测试。没有在微信真机验证扫码、激活、通知与预约闭环。
- 本地有实现不等于已发布到微信；报告中的“已有能力”均指代码存在。后续宣传素材必须与实际小程序发布版本再次核对。

## 3. 目标用户与购买动机

| 优先级／画像假设 | 当前工作方式与痛点 | 官网要回答的问题 | 最有说服力的证据 |
|---|---|---|---|
| 首要：独立美甲师／单人预约制工作室 | 用微信聊天接单，手工核对档期，既服务又运营 | 客户预约是否更方便？我是否会增加操作负担？ | 客户选时间→美甲师查看预约的真实连贯演示 |
| 首要：重视审美与长期关系的定制工作室 | 风格展示、沟通报价、服务偏好散落在聊天里 | 能否展示专业度、保留每次服务细节？ | 专属主页、作品、报价、客户服务记录 |
| 次要：提供上门服务的独立美甲师 | 时间、地点、服务状态需要一起确认 | 上门与到店能否准确区分？ | 对应服务配置与预约信息；不描述为自动最优路线规划 |
| 后续：刚开始独立经营的美甲师 | 没有稳定客户，也不熟悉工具 | 能否带来客户？入驻后如何开始？ | 明确需自己经营获客，提供开通清单和分享入口 |
| 暂不主攻：多店连锁／多员工复杂经营 | 排班、提成、库存、财务与权限复杂 | 能否替代完整门店 ERP？ | 当前不作此承诺，不为官网招募扩建整套连锁系统 |

美甲师决策链：**是否适合我 → 能解决什么具体问题 → 客户愿不愿意用 → 怎么开通 → 收费及退出规则 → 提交申请。**

优先验证的三条假设：预约效率比“大而全”更有吸引力；真实小程序演示比纯美甲作品更能解释工具价值；清晰的开通陪同与费用说明能够降低申请犹豫。这里的“更”需要访谈和试招募验证。

## 4. 小程序功能与卖点证据矩阵

证据等级：A＝前端调用与后端实现可追踪；B＝本地页面/模块有实现，但本轮未完整追踪运行条件；C＝运营承诺或发布状态需外部确认。A、B 均不等于真机验收通过。

| 功能／证据 | 官网建议卖点 | 边界与优先级 |
|---|---|---|
| 专属主页、作品、服务、评价入口（A）：`client-wxapp/pages/client/artist-home/index.js`；`backend/src/technician-works/public-brand.service.ts` | 把作品、服务和预约入口放在自己的美甲师主页 | 首屏核心；具体展示取决于公开状态、授权与资料完整性 |
| 客户预约、熟客快捷预约（A）：`pages/client/quick-booking/index.js`、`create-order/`；`backend/src/orders/` | 把反复确认时间变成可查看的预约记录 | 核心；快捷预约存在配置开关，不承诺任何客户无条件免登录 |
| 每日接待上限、预约间隔、日期开放（A）：`pages/technician/profile/index.js`；`booking-days.service.ts` | 自己掌握每天接待量，为服务之间留出准备时间 | 差异化核心；当前代码支持上限 1–10、间隔 15–180 分钟，不沿用旧 PRD 1–3 位的范围 |
| 设计沟通与报价（B）：小程序 `design-requests/`、`chat-detail/`、`order-detail/`；后端 `client-designs/`、`orders/` | 灵感沟通与报价有记录 | 二级场景；不把“有记录”写成完全替代微信沟通 |
| 客户档案与跟进（A）：`pages/technician/customer-detail/index.js` 中标签、跟进创建/完成调用 | 记住客户偏好和服务经历，方便后续跟进 | 核心；不是保证客户复购或自动营销触达 |
| 完成服务记录（A）：`complete-service/index.js`；`orders.service.ts` | 记录实际金额、耗材、甲面情况和护理建议，关联作品 | 新版值得重点展示的能力；资料需要美甲师主动填写 |
| 经营数据与导出（A）：`business-data/index.js`；`backend/src/revenues/revenues.service.ts` | 查看经营记录，导出客户、订单、作品信息与收入记录 | 应说明文件范围、时间范围与权限；导出记录不等于所有媒体原文件可完整迁移 |
| 作品分享、物料、转介绍（A/B）：`marketing-materials/`、`referral-campaign/`；`work-share-code.service.ts` | 将作品和预约入口分享给客户 | 支持获客承接，不保证平台免费派单；分享授权与微信能力需验收 |
| 通知与提醒（B/C）：`components/subscription-onboarding/` 及 10 月 12 日通知计划 | 授权后接收适用的预约消息 | 模板、授权、平台配置与发布状态待验收；不宣传“绝不漏单、永久自动提醒” |
| 申请审核（A，但链路待补）：`artist-applications.service.ts`、管理后台 `ArtistApplications.tsx` | 提交申请，经审核后开通 | 审核通过创建账号，但没有在这条方法内自动生成/发送 16 位激活 Key |

### 必须纠正或确认的宣传口径

- “收入自动统计”应改为“按已记录的服务完成金额汇总经营收入”。新版完成服务允许填写 `actualAmount`，后端据此建立收入记录；它不证明银行卡实际到账或财务利润。
- “100% 数据归美甲师”过于绝对。建议解释可查看、导出哪些本人经营数据，以及客户隐私、授权、退出处理方式；不作未经核实的所有权或完整可迁移承诺。
- “预约不漏单”改为“预约集中管理”，避免结果保证。
- “不抽成”“免费试用”“随时取消”“1–2 个工作日”属于经营政策。代码和页面文案不能单独证明执行能力，发布前须由负责人确认具体条件。
- 容量管理、客户跟进与服务档案比“1 个小程序”更值得占据首页价值区。

上述比较支持一个**产品策略推断**：OnlyNail 应在“美甲细分、个人品牌、手机经营、微信客户承接”上形成清晰认知，而非用功能数量与综合 SaaS 竞争。此判断不是市场份额或竞争壁垒的实证结论。

官网流量建议先来自已有美甲师关系、同行推荐、公众号及内容介绍。小红书等渠道用于场景内容测试；具体外链和引导规则须在投放前核查，不预设外链在所有平台畅通。官网本身不会自动产生客源。

## 7. 推荐官网结构与内容需求

### 首页顺序

1. **首屏定位**：谁使用、解决什么、主行动。建议标题“把预约和老客，管理得更从容”；副标题“给独立美甲师的微信经营工具：展示作品、安排预约、保留服务记录，在手机上处理日常经营”。主 CTA“申请入驻”，辅 CTA“看看怎么用”。标题为候选文案，不是最终品牌定稿。
2. **快速自我判断**：独立接单、个人工作室、预约制服务；说明已拥有微信客户也能使用，无需误以为只适用于上门。
3. **三个真实场景**：分享主页→客户预约；管理接待容量→安排服务；完成服务→客户记录与后续跟进。每个场景用新版截图、简短说明和明确前后结果。
4. **真实工作室案例**：先展示一个完整案例，说明使用方式；没有授权或效果数据时标为功能演示，不伪造证言、商家数或增收数字。
5. **入驻权益与费用**：当前可用能力、是否收费、试用条件、是否续费、是否抽成与退出方式。政策未定时明确为邀请体验并提供咨询，不展示空价格表。
6. **开通四步**：申请→人工审核与联系→获取激活方式→完善主页和预约设置。激活后应引导发布作品、设置服务及营业时间，不把“注册成功”当作已可接单。
7. **首页 FAQ**：是否帮助获客、客户如何进入、到店/上门支持、费用、信息导出与退出、审核后做什么、如何联系。
8. **结尾申请**：直接申请按钮和次级真实联系入口；公众号作为可选更新渠道。

## 8. 功能需求与最小技术方案

### 申请与开通

核心字段保留姓名、手机号、城市、微信号；称呼可由负责人决定是否替代实名姓名。服务模式用明确的 home/shop/both 选项；若仍允许不填，审批前由运营补全，不能默默生成不可服务账号。经验、风格与补充说明折叠为选填。字段用途就近解释。

服务端承担校验、去重和状态控制。前端预查不能防并发重复，也不能把 approved 简单等同于已激活；需区分“已申请”“审核通过待开通”“已激活”的实际事实。对公众不通过任意手机号直接暴露内部状态。首期可统一返回“已收到，我们将按当前进度联系”，身份验证查询入口视需求后置。

后台复用已有申请与 technicians 能力：审批后显示关联账号，进入现有 Key 生成/复用流程，记录人工联系与交付情况。16 位美甲师激活 Key 与 8 位客户邀请 code 必须明确区分；不将激活 Key 暴露给未认证的官网或记入公开埋点。首期人工交付足够，不为官网新建微信客服机器人。

### 体验入口

手机先在官网展示真实演示，不强迫离开；需要打开小程序时，再提供已验证的路径、搜索名称和扫码兜底。桌面显示小程序码及目标说明。是否能直接打开取决于实际账号与平台能力，必须在微信、iOS Safari、Android 浏览器验证。

已有 `WorkShareCodeService.generateInviteLink` 是**客户邀请链接**，不能原样当成美甲师开通入口。可以复用服务端凭证获取的既有机制，但需定义正确目标与权限。本轮微信 URL Link 官方文档读取失败，因此不把当前资格、额度或浏览器兼容性写成已验证事实。

### 内容、图片、搜索与分享

继续用当前 React/Vite，先用代码管理少量文案与授权案例。首页关键产品证据不要依赖生产作品列表才能显示；动态作品失败时有真实空态。压缩图片、明确尺寸、首屏图片优先、下方懒加载。补默认分享图、规范标题与路由、404 和链接巡检；有明确搜索获客需求再评估预渲染，不为 SEO 先换框架。OG 标签不能代替微信分享卡片实机验证。

### 招募数据闭环

现有 conversion-events 要求 technicianId，事件只有 artist_view、work_view、booking_intent 等，不能把“申请入驻”硬塞进去。首期在申请记录保存经过校验的来源代码、活动代码与关联美甲师 ID；审核、激活、首次配置状态优先从后端事实取得。

若需要匿名访客漏斗，再加最小事件：landing_view、demo_open、apply_start、apply_submit_success。后两项中成功只能在服务器确认成功后产生；审核/激活事件不得由浏览器伪造。渠道参数白名单化，不传手机号、微信号、Key；二维码打开与真实激活不能视为同一事件。

本报告不提供行业转化率基准或收益预测。试招募以“合适的人能独立理解并完成开通”为第一验证目标，再根据真实样本判断是否扩张。

| 维度 | 判断 | 前置条件 |

| 大范围商业获客 | 尚无法证明 | 缺少流量、有效申请、激活使用与成本数据 |

**建议投入上限由两段决策控制：**先做最小闭环与新版宣传页，再决定是否做更复杂的演示、自动通知和投放落地页。首期暂不做多城市招商系统、订阅支付重构、营销自动化、全套 CRM、AI 获客承诺、多店管理或原生 App 下载推广。

计划估算为 19–28 人日，按一位熟悉项目的全栈开发、设计/产品及运营支持计算，约 4–6 周；不含新订阅支付、微信资质办理、大规模素材拍摄及发布审批等待。它是任务拆分估算，不是已确定交期或费用报价，详见开发计划。

发布后先邀请 5–8 位符合画像的美甲师做任务式访谈与陪同试用，这是建议研究样本而非统计显著性标准：请其解释产品、寻找费用、看演示、提交测试申请、开通并设置首个服务/档期。记录卡点及完成所需帮助，不只问“喜不喜欢”。同时准备 1 个经授权的工作室案例。

扩张门槛：没有阻断级错误；真实申请可追踪到开通；运营能履行对外时效；新人能完成资料、服务、档期及首个作品设置；确认线上允许目标美甲师访问。未通过时维持邀请制或改为意向登记，不扩大投放。
