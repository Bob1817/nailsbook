# NailBook 第一阶段上线验收与发布准备清单

> 建立日期：2026-09-09<br>
> 适用范围：微信小程序（客户与美甲师双角色）、后端 API、超管后台、生产环境与首发运营内容<br>
> 当前结论：**No-Go，进入上线准备阶段，尚未达到正式发布条件。**

## 1. 上线目标

第一阶段上线必须同时达到以下结果：

1. 客户能够完成登录、绑定美甲师、浏览作品、预约、确认报价、取消预约和查看服务结果。
2. 美甲师能够完成登录、切换角色、管理作品、设置客户首页推荐、处理预约、确认价格与定金、完成服务和查看收入。
3. 超管能够完成美甲师、客户、作品审核和关键配置管理，敏感操作有权限控制及审计记录。
4. 首发范围符合“小程序仅作为指定门店到店预约与经营管理工具”的合规定位，不开放上门服务、平台撮合或在线支付。
5. 候选版本可以从干净代码提交重复构建；数据库可以备份、迁移和恢复；上线异常时可以回滚。
6. iPhone 与 Android 真机均完成双角色核心闭环验收，并保留版本、账号、订单号和截图证据。
7. 生产环境具备健康检查、日志、备份、证书续期和故障联系人，上线后关键指标可被观察。

## 3. 优先级任务列表

### P0：上线阻断任务

P0 全部关闭且证据齐全后，项目才能进入正式发布窗口。

#### P0-01 冻结首发范围并建立唯一候选版本

**目标：** 所有人验收的是同一份代码、配置和数据库迁移。

- [ ] 明确首发端：微信小程序、后端、超管后台；确认其他 Web/Flutter/iOS 是否随本次发布。
- [ ] 冻结第一阶段功能，不再混入非阻断型需求。
- [ ] 盘点当前所有已修改和未跟踪文件，区分应发布、试验文件、验收产物和本地配置。
- [ ] 将应发布改动拆分为可评审提交，完成代码审查。
- [ ] 从干净检出创建发布候选提交和版本号，例如 `v1.0.0-rc.1`。
- [ ] 记录 commit SHA、数据库迁移最高版本、小程序版本号和各镜像摘要。

**通过标准：** `git status` 干净；候选版本可被重新检出；不存在依赖某台电脑未提交文件的构建。

#### P0-02 产品范围与业务规则签字

**目标：** 上线行为有唯一解释，前后端和运营使用同一规则。

- [ ] 产品确认订单状态机：提交、待确认、已确认、服务中、已完成、取消、拒绝及允许操作人。
- [ ] 确认排期弹窗的最终报价、定金金额、定金支付状态及订单展示规则。
- [ ] 确认作品状态语义：草稿、待审核、审核通过、已拒绝、隐藏、归档与公开访问。
- [ ] 确认客户首页推荐规则：每位美甲师最多 3 个、满额替换、可取消推荐、客户侧总展示上限与排序。
- [ ] 确认客户绑定美甲师上限及“我的美甲师”折叠/查看更多规则。
- [ ] 确认双角色账号切换、退出登录和数据隔离规则。
- [ ] 明确首发不支持的能力及对应页面文案，避免出现可点击但必然失败的入口。

**通过标准：** 以上规则形成一页最终版产品确认记录，产品负责人签字；测试用例与该记录一致。

#### P0-03 核心业务端到端验收

**目标：** 使用真实客户端和美甲师端完成同一订单闭环，数据与金额一致。

- [ ] 准备隔离测试环境及客户 A、客户 B、美甲师 A、美甲师 B、超管账号。
- [ ] 客户注册/登录、协议同意、绑定美甲师；验证绑定上限及重复绑定。
- [ ] 美甲师登录并切换客户/美甲师角色；验证退出后令牌和页面状态清理。
- [ ] 美甲师发布作品 → 超管审核 → 公开详情可访问 → 推荐至客户首页 → 满额替换 → 取消推荐。
- [ ] 客户从首页 Hero 进入正确作品，绑定多个美甲师时数量、去重和排序符合规则。
- [ ] 客户创建标准预约，重复点击不产生重复订单；美甲师确认排期、修改价格和定金信息。
- [ ] 覆盖自定义需求的报价、客户接受/拒绝、重新报价。
- [ ] 覆盖改期、客户取消、美甲师拒绝，验证双方状态与档期同步。
- [ ] 完成服务并核对订单金额、收入、服务记录、客户统计；重复完成不重复入账。
- [ ] 客户 A/B、美甲师 A/B 互相不能读取或修改对方数据。

**通过标准：** 所有路径有订单号/作品 ID、预期与实际结果、截图；无 P0/P1 未解决缺陷。

#### P0-04 真机、兼容性与异常验收

**目标：** 主流手机和弱网场景中不存在白屏、遮挡、误操作或重复写入。

- [ ] 至少一台 iPhone 和一台 Android 完成 P0-03 主路径。
- [ ] 记录系统版本、微信版本、小程序基础库版本和候选 commit。
- [ ] 检查 iPhone 刘海/灵动岛、底部安全区、Android 返回键和不同屏幕宽度。
- [ ] 检查输入法弹起时登录、报价、定金、评论和预约提交按钮不被遮挡。
- [ ] 检查无网、弱网、超时、接口 401/403/404/429/500 的提示及恢复。
- [ ] 检查连续点击、返回重进、前后台切换和登录过期不造成重复订单或串号。
- [ ] 检查图片上传失败、权限拒绝、超大图片和中途取消。
- [ ] 检查分享卡片、二维码、冷启动、登录后回跳到正确作品和美甲师。

**通过标准：** 两类真机核心流程通过；阻断缺陷清零；一般缺陷有明确规避方式和修复日期。

#### P0-05 合规、资质与微信平台配置

**目标：** 提审内容、代码能力和实际经营范围一致。

- [ ] 确认小程序主体、服务类目、名称、简介、图标和截图与首发定位一致。
- [ ] 确认首发仅支持到店服务；客户端、美甲师端、接口及审核素材不出现上门服务入口。
- [ ] 确认在线支付关闭，页面明确为线下付款；不得保留可触发支付的首发入口。
- [ ] 配置并核实运营主体、门店名称、地址、电话、隐私联系人和备案号。
- [ ] 在微信公众平台更新《用户协议》《隐私政策》和隐私保护指引，声明实际使用的数据与接口。
- [ ] 验证协议主动勾选、隐私授权拒绝、撤回授权、账号注销和数据删除流程。
- [ ] 检查用户上传作品、评论、聊天等内容的审核、举报、删除与审计机制。
- [ ] 确认微信登录配置真实有效；若订阅提醒未获批或未配置，首发关闭相关入口。
- [ ] 准备微信审核说明、测试账号、操作路径和特殊功能说明。

**通过标准：** 生产就绪检查脚本通过；微信后台配置截图归档；法务/运营负责人确认提审材料。

#### P0-06 安全与生产配置验收

**目标：** 生产环境不使用默认口令、测试密钥或宽松权限。

- [ ] 删除或修改文档中的默认超管口令使用方式；生产超管使用强随机密码并强制重置。
- [ ] 轮换并独立保存 Admin、Technician、Client JWT 密钥及系统配置加密密钥。
- [ ] 核对 `.env`、日志、仓库历史和构建产物中无真实密码、JWT、AppSecret、商户密钥或私钥。
- [ ] 收紧 CORS、可信代理、上传类型/大小、登录/验证码/公开接口限流。
- [ ] 复验超管 RBAC：无权限 403、未登录 401、禁用账号立即失效、敏感操作写入审计日志。
- [ ] 验证客户、美甲师、管理员三类令牌不能跨角色调用接口。
- [ ] 检查生产数据库、上传目录、备份文件的文件权限和宿主机访问权限。

**通过标准：** 安全检查无高危项；所有生产密钥来自正式密钥库或受限环境文件；默认账号不可用于生产。

#### P0-07 数据库迁移、备份与回滚演练

**目标：** 升级失败时可以在明确时间内恢复服务和数据。

- [ ] 确认 schema 中每项发布变更都有对应 Prisma migration，包括作品创建幂等、推广、Hero 与绑定上限。
- [ ] 在生产副本执行 `prisma migrate deploy/status/diff`，结果无未应用迁移和 schema 差异。
- [ ] 上线前使用 SQLite online backup 创建快照，并验证 `integrity_check=ok`、外键无异常和核心表数量。
- [ ] 执行一次“备份 → 迁移 → 启动 → 冒烟 → 恢复旧版本与备份”的完整演练。
- [ ] 明确停写窗口、数据恢复点目标、允许的数据损失窗口和回滚决策人。
- [ ] 核对自动备份定时任务、保留 30 份策略、磁盘余量和异机备份。

**通过标准：** 恢复后的数据库可启动旧版本并通过只读冒烟；演练耗时和命令被记录。

#### P0-08 候选版本自动化门禁

**目标：** 所有发布产物来自同一干净候选提交，任何核心检查失败即停止发布。

- [ ] 后端：`npm test -- --runInBand && npm run build`。
- [ ] 超管后台：`npm run lint && npm run build`。
- [ ] 实际发布的其他 Web 端：分别运行生产构建。
- [ ] 官网：`npm run test:run && npm run build`。
- [ ] 小程序：`node scripts/release-gate.js`。
- [ ] 设计颜色：`python3 scripts/sync-colors.py --check && python3 scripts/check-colors.py`。
- [ ] 若 Flutter/iOS 属于本次范围，执行对应测试及 Release 构建；否则从发布清单中明确排除。
- [ ] 远端 CI 全绿，镜像 job 依赖所有测试和构建任务成功。
- [ ] 将日志、测试数量、产物校验值和 CI 链接归档到本次发布目录。

**通过标准：** 干净环境全量通过；没有跳过测试、放宽断言或手工替换构建产物。

#### P0-09 生产部署、冒烟与回滚准备

**目标：** 上线过程可执行、可观察、可中止。

- [ ] 指定发布负责人、后端/数据库负责人、产品验收人和回滚决策人。
- [ ] 确定低峰发布窗口、停写时间、通知渠道和最大允许中断时间。
- [ ] 使用 commit SHA 镜像标签部署，记录部署前后版本，禁止仅依赖 `latest`。
- [ ] 先部署兼容后端并完成迁移，再部署管理后台，最后上传小程序候选版本。
- [ ] 验证 API、管理后台、域名、TLS、上传资源和数据库连接健康。
- [ ] 用生产测试账号执行登录、作品公开访问、Hero、预约查询和权限冒烟；不创建无清理方案的演示数据。
- [ ] 检查错误日志、CPU、内存、磁盘、429/5xx、接口延迟和容器重启次数。
- [ ] 预先写好回滚命令：旧镜像、旧配置、数据库恢复路径及 DNS/Nginx 处理方式。

**通过标准：** 冒烟全部通过且监控稳定；异常可在约定时限内回滚；发布记录完整。

### P1：上线前必须完成的质量任务

P1 原则上在发布前关闭；确需延期时必须有负责人、日期和不会影响核心交易/数据安全的依据。

- [ ] 对客户、美甲师、超管三端进行一次完整文案校对，统一状态名、金额单位和操作结果提示。
- [ ] 对首页、登录、作品、预约、订单、客户、消息、个人页进行视觉验收，检查 44px 触控区、字号、安全区和加载/空/失败状态。
- [ ] 核对所有 404：页面路由、公开作品、图片 URL、分享链接和 API 版本不能指向已删除资源。
- [ ] 核对金额均使用“分”作为服务端存储/传输边界，展示换算、优惠、定金和收入无精度错误。
- [ ] 核对时间、时区、跨天服务、休息日、排班冲突和过期预约。
- [ ] 核对正式门店资料、服务名称、价格、时长、排班、作品封面及审核状态。
- [ ] 清理或隔离演示账号、演示订单和测试作品，保留必要审核账号并设置有效期。
- [ ] 验证客服/反馈入口有人接收，明确回复时效和升级路径。
- [ ] 建立缺陷表：严重级别、复现步骤、负责人、修复版本、复验结果。
- [ ] 编写一页客服与运营手册：登录、审核、改价、取消、退款说明、账号异常和用户投诉处理。

### P2：上线后首周完善任务

- [ ] 建立核心漏斗：访问 → 登录 → 绑定 → 查看作品 → 提交预约 → 确认 → 完成。
- [ ] 建立业务指标：预约成功率、取消率、报价接受率、完成率、平均客单价和复购。
- [ ] 建立技术指标：可用率、P95 延迟、5xx、429、登录失败、上传失败、任务失败和磁盘容量。
- [ ] 每日检查备份结果并抽检恢复；首周至少再做一次异机恢复。
- [ ] 收集首批客户和美甲师反馈，只处理阻断使用、金额错误、数据错乱和高频体验问题。
- [ ] 对首周缺陷做复盘，形成 v1.0.1 范围；非紧急体验优化进入后续迭代。

## 4. 建议执行顺序与里程碑

| 阶段 | 建议时间 | 进入条件 | 退出条件 |
|---|---:|---|---|
| M1 范围冻结 | 0.5–1 天 | 第一阶段开发基本完成 | P0-01、P0-02 完成，形成 RC1 |
| M2 自动化与安全 | 1–2 天 | RC1 可构建 | P0-06、P0-08 通过，无高危问题 |
| M3 业务与真机验收 | 2–3 天 | 独立测试环境可用 | P0-03、P0-04 通过，P1 缺陷完成收敛 |
| M4 合规与内容 | 可与 M2/M3 并行 | 正式主体资料齐全 | P0-05 完成，提审材料齐全 |
| M5 发布演练 | 0.5–1 天 | RC 稳定且迁移冻结 | P0-07、P0-09 演练完成，形成 RC2 |
| M6 提审与发布 | 依微信审核周期 | Go/No-Go 会议结论为 Go | 审核通过、生产冒烟通过、监控稳定 |
| M7 上线观察 | 发布后 7 天 | 正式版本可访问 | P2 指标持续观察并完成首周复盘 |

以上时间是执行工作量估算，不包含微信审核等待和资质办理时间。

## 6. 缺陷分级与发布决策

| 级别 | 定义 | 发布规则 |
|---|---|---|
| P0 | 无法登录/预约/审核/完成服务；越权或数据泄露；金额错误；数据丢失；无法迁移或回滚；合规阻断 | 必须修复并复验，任何一个未关闭均 No-Go |
| P1 | 核心流程可继续但明显误导、状态不一致、主要设备严重遮挡、失败后无法恢复 | 原则上修复；延期必须由产品和发布负责人共同接受 |
| P2 | 不影响任务完成的样式、低频提示或运营优化 | 可进入上线后版本 |

Go/No-Go 会议只检查证据，不以“开发已完成”代替验收。以下条件全部满足才能选择 **Go**：

- [ ] P0 全部关闭，P1 有明确结论。
- [ ] 最终 RC 的 CI、构建、迁移、备份恢复、双真机和生产冒烟证据齐全。
- [ ] 微信提审配置、正式内容和测试账号已准备。
- [ ] 发布与回滚负责人在线，旧版本和数据库备份可用。
- [ ] 产品负责人、技术负责人、运营/合规负责人和发布负责人共同签字。
