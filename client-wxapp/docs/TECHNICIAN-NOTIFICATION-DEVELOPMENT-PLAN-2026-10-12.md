# 美甲师通知闭环开发计划

日期：2026-10-12  
适用范围：OnlyNail 微信小程序、单人美甲工作室  
当前约束：不使用短信、不使用企业微信、不依赖原生 App

## 1. 目标与产品边界

本计划只使用美甲师日常已有的微信和手机系统完成通知闭环，尽量降低学习和操作成本：

1. 预约和客户消息通过微信订阅消息主动触达；
2. 已确认预约写入手机系统日历，降低忘记行程的风险；
3. 小程序在前台时使用即时横幅、震动和红点提醒；
4. 每天首次进入小程序时自动汇总尚未处理的事项；
5. 每次授权、发送、失败、查看和处理均有记录。

必须明确：在没有短信、企业微信或原生 App Push 的情况下，微信小程序不能任意向退出小程序的用户推送消息。离线触达依赖用户主动授予的一次性订阅消息权限；权限耗尽或系统通知被关闭后，无法保证百分之百触达。

因此本阶段的目标是“在平台允许的范围内提高触达率”，不对所有客户聊天作绝对送达承诺。

## 2. 当前代码基线

已存在能力：

- `WechatSubscribeMessagesService` 支持新预约、客户预约成功、预约日前和临近提醒；
- `OrdersScheduler` 已按 `Asia/Shanghai` 处理日前和临近预约提醒；
- 客户创建预约和订单详情已有订阅授权入口；
- 美甲师报价/确认组件会请求一次美甲师订阅授权；
- 双端已有会话、未读数量、标记已读和站内系统消息；
- 美甲师首页已有“待处理事项”和“下一单”。

需要补齐的问题：

- 美甲师没有持续可见、足够简单的提醒开通入口；
- `WechatSubscriptionAuthorization` 只保存最后一次状态，没有可发送次数和消费记录；
- 客户确认报价、拒绝报价、取消和改期没有完整的美甲师订阅通知；
- 客户聊天没有符合场景的订阅模板和未读聚合策略；
- 小程序前台收到消息时缺少足够明显的即时提醒；
- 已确认预约不能加入手机系统日历；
- 没有统一的通知事件、发送结果、去重和处理记录。

## 3. 简化后的通知体系

### 3.1 微信订阅消息

美甲师端优先使用三个核心模板：

| 模板 | 使用事件 | 优先级 |
| --- | --- | --- |
| 新预约提醒 | 客户提交新预约 | P0 |
| 预约状态变更 | 客户确认报价、拒绝报价、取消、改期 | P0 |
| 新咨询/留言提醒 | 客户消息连续未读 5 分钟后聚合提醒 | P0 |

现有日前和临近预约模板继续保留，但对美甲师端不占用首页首批授权位置：已确认预约主要由手机日历承担行程提醒；在报价确认、查看预约等自然操作中再补充申请日前和临近提醒。客户端仍沿用现有预约提醒策略。

普通聊天内容不能套用预约模板。只有在微信公众平台存在并审核通过符合场景的“新咨询/留言提醒”模板时，才启用聊天离线订阅提醒；模板不可用时，只执行站内未读和前台提醒。

### 3.2 手机系统日历

预约进入 `pending_shop` 后，预约详情和首页“下一单”显示一个主要操作“加入日历”。写入内容：

- 标题：`OnlyNail｜客户昵称｜服务项目`；
- 开始、结束时间：使用预约锁定时间；
- 地点：门店名称和地址；
- 说明：预约号、客户电话掩码、服务项目；
- 系统提醒：默认提前 2 小时，最终以手机系统支持为准。

小程序记录订单 ID、预约版本和时间指纹。预约改期后提示“时间已变化，请重新同步日历”；取消后提示删除原日历事项。第一阶段不假设微信 API 可以可靠修改或删除既有系统日历事件。

### 3.3 小程序前台提醒

当美甲师正在使用小程序时：

- 新客户消息由现有 HTTPS 轮询发现后显示顶部横幅；
- 对新预约、取消、改期和客户消息执行一次短震动；
- 横幅包含客户昵称、事件摘要和“立即查看”；
- 相同会话 10 秒内的多条消息合并，不连续震动；
- 当前正在查看对应会话时不显示重复提醒；
- 底部消息红点和首页待处理数立即更新。

声音提醒需经过真机验证，首期以震动和视觉横幅为确定能力，避免依赖可能受系统静音或播放策略限制的声音。

### 3.4 每日首次进入摘要

美甲师每天第一次进入小程序时，如果存在待处理内容，展示一个简单摘要层：

- 今日和明日预约；
- 待报价、待处理变更；
- 未读客户会话；
- 尚未同步到日历的已确认预约。

摘要只保留两个操作：“去处理”和“稍后”。当天已查看且无新增重要事项时不重复弹出。首页待处理卡片继续永久展示未完成事项。

### 3.5 一次性简单引导

通知设置不设计复杂开关矩阵，只提供一个“提醒保障”页面和三个状态：

- `需要开启`：没有可用订阅授权；
- `需要补充`：任一核心模板可用次数不足；
- `提醒正常`：三个核心模板均有可用次数。

页面仅提供：

1. 一个“开启/补充微信提醒”按钮；
2. 一个“检查微信通知设置”入口；
3. 手机日历说明；
4. 最近通知结果。

首次设置时用三步说明引导美甲师开启微信系统通知、允许服务通知，并把 OnlyNail 收藏到“我的小程序”。不要求美甲师理解模板 ID、授权次数或渠道概念。

## 4. 授权补充策略

订阅授权只能由用户点击触发，不能在 `onLoad` 或 `onShow` 自动弹出。为了不增加复杂操作，把授权融入原有自然动作：

1. 首页提醒卡片：点击“开启接单提醒”时申请新预约、状态变更、新咨询三个模板；
2. 确认报价：现有“确认方案”点击中申请状态变更、日前、临近三个模板，授权失败不阻断报价；
3. 客户聊天：当咨询模板次数不足时，在输入区上方显示一次轻量“开启新消息提醒”；用户点击后只申请咨询模板；
4. 查看待到店预约：日历未同步时优先提示加入日历，不反复弹出订阅授权；
5. 用户拒绝后 7 天内不重复强提示；状态为 `ban` 时只提供打开设置的说明。

后台精确记录每个模板的可用次数，但前端只显示“需要补充/提醒正常”。

## 5. 事件和触达规则

| 事件 | 订阅消息 | 站内消息 | 前台横幅/震动 | 日历 |
| --- | --- | --- | --- | --- |
| 新预约 | 立即发送 | 是 | 是 | 否 |
| 客户确认报价 | 立即发送 | 是 | 是 | 提示加入 |
| 客户拒绝报价 | 立即发送 | 是 | 是 | 否 |
| 客户取消预约 | 立即发送 | 是 | 是 | 提示删除旧事项 |
| 客户改期 | 立即发送 | 是 | 是 | 提示重新同步 |
| 客户聊天 | 未读满 5 分钟后聚合发送 | 是 | 是 | 否 |
| 明日预约 | 有对应授权时发送 | 是 | 否 | 已确认预约由日历负责 |
| 临近预约 | 有对应授权时发送 | 是 | 否 | 默认提前 2 小时提醒 |

客户聊天聚合规则：

1. 同一会话第一条未读消息满 5 分钟后检查；
2. 仍未读且咨询模板有可用次数，发送一条“某客户发来 N 条新消息”；
3. 只展示客户昵称、消息数量和最后一条消息类型，不发送完整聊天内容；
4. 美甲师进入会话并标记已读后结束本轮升级；
5. 授权不足时保留高优先级站内待办，下一次进入小程序时在每日摘要顶部显示。

## 6. 技术方案

### 6.1 订阅授权次数

对 `WechatSubscriptionAuthorization` 增加：

- `availableCount`：当前可发送次数；
- `acceptedCount`：累计接受次数；
- `consumedCount`：累计成功发送次数；
- `lastAcceptedAt`、`lastConsumedAt`；
- `lastErrorCode`、`lastErrorMessage`。

每次微信返回 `accept` 时为对应模板增加一次可用次数；成功发送后原子扣减一次。发送失败时按错误码决定保留次数、清零或要求重新授权，并记录失败原因。

历史 `accept` 无法确定是否已被微信消耗，迁移后不直接转换成可用次数，要求重新点击授权，避免显示虚假的“提醒正常”。

### 6.2 统一通知事件

新增 `NotificationEvent`：

- `eventKey`：唯一事件键；
- `eventType`；
- `recipientRole`、`recipientId`；
- `orderId`、`conversationId`、`messageId`；
- `priority`；
- `status`：`pending/sending/delivered/failed/resolved`；
- `availableAt`、`resolvedAt`；
- `payloadSnapshot`；
- 创建和更新时间。

新增 `NotificationDelivery`：

- `notificationEventId`；
- `channel`：`in_app/wechat_subscribe/calendar`；
- `status`：`pending/sent/failed/skipped`；
- `attemptCount`、`sentAt`；
- `providerCode`、`providerMessage`；
- `dedupeKey`。

预约和聊天事务只写通知事件，异步任务负责发送。事件键至少包含事件类型、订单/会话 ID 和业务版本，确保接口重试不会重复通知。

### 6.3 预约事件接入点

- 创建预约：`booking.created`；
- 美甲师发送或修改报价：`booking.quote_sent`；
- 客户确认报价：`booking.quote_accepted`；
- 客户拒绝报价：`booking.quote_rejected`；
- 任一方取消或驳回：`booking.cancelled/rejected`；
- 预约时间修改：`booking.rescheduled`；
- 定时提醒：`booking.day_before/hour_before`。

打开预约详情、完成报价、取消或确认服务后，解决对应待处理通知。首页待处理数仍以真实订单状态计算，通知表只用于发送审计和未读升级。

### 6.4 聊天未读升级任务

增加每分钟运行的轻量任务：

- 查询接收人为美甲师、未读且创建超过 5 分钟的客户消息；
- 按会话聚合，检查本轮是否已经生成通知；
- 有咨询模板授权时创建并发送订阅消息；
- 无授权时只保留站内高优先级状态；
- `markAsRead` 后把对应升级事件标记为 `resolved`。

### 6.5 前台实时提醒

在小程序应用层增加统一事件分发，不在各页面重复实现：

- 复用现有 HTTPS 会话轮询，不为小程序额外引入 Socket 客户端；
- 应用前台时触发一次短震动和全局横幅；
- 事件按 `eventKey` 去重；
- 页面恢复前台时刷新未读数和关键预约状态；
- 横幅跳转前处理登录过期和角色校验。

## 7. 分阶段开发计划

### 阶段 A：授权次数和通知事件基础（P0）

预计工作量：2–3 个开发日。

开发内容：

- 数据库增加授权次数、通知事件和发送记录；
- 改造 `sendAuthorized`，增加原子消费、幂等和失败记录；
- 增加美甲师提醒状态接口；
- 覆盖重复授权、并发消费、失败不误扣和历史迁移测试。

验收标准：

- 一次授权只消费一次；
- 重复任务不重复发送；
- 微信失败原因可查询；
- 历史状态不会错误显示为可发送。

### 阶段 B：简化提醒入口和预约状态通知（P0）

预计工作量：2–3 个开发日，依赖阶段 A 和预约状态模板。

开发内容：

- 首页“开启接单提醒”卡片；
- 简化的提醒保障页；
- 新预约、客户确认、拒绝、取消、改期通知；
- 通知点击进入对应预约详情；
- 在报价等自然动作中补充授权。

验收标准：

- 全程不出现模板 ID、次数等技术词；
- 授权只能由明确点击触发；
- 五类关键预约事件均正确通知并去重；
- 授权失败不阻断预约业务操作。

### 阶段 C：客户消息未读升级和前台强提醒（P0）

预计工作量：2–3 个开发日，离线提醒依赖咨询/留言模板。

开发内容：

- 客户聊天 5 分钟未读聚合；
- 咨询订阅模板发送和授权不足降级；
- 全局前台横幅、短震动和实时未读更新；
- 每日首次进入摘要。

验收标准：

- 同一会话连续多条消息只发送一条聚合通知；
- 五分钟内已读不发送订阅消息；
- 当前会话不重复横幅和震动；
- 当天无待办时不显示每日摘要。

### 阶段 D：系统日历（P1）

预计工作量：1–2 个开发日。

开发内容：

- 预约详情和“下一单”的加入日历操作；
- 权限拒绝和恢复说明；
- 订单版本和时间指纹记录；
- 改期、取消后的日历处理提示。

验收标准：

- iPhone 和 Android 真机均写入正确时间、门店和说明；
- 系统提醒按支持情况设置为提前 2 小时；
- 改期后明确要求重新同步；
- 重复点击有明确提示，不静默创建重复事项。

### 阶段 E：回归与上线（P1）

预计工作量：1–2 个开发日。

开发内容：

- 通知成功率、失败原因和未处理时长查询；
- 后端迁移、构建和定向测试；
- 小程序静态检查和双平台真机测试；
- ECS 后端部署与微信小程序上传分别执行和记录。

验收标准：

- 每个关键事件都能查询生成、发送和处理结果；
- 通知失败不影响预约和聊天主流程；
- 新预约、确认、拒绝、取消、改期、聊天未读、日前、临近和日历完成真机验证。

预计总工作量：8–13 个开发日。

## 8. 外部准备清单

阶段 B 前：

- 在微信公众平台确认或新增“预约状态变更提醒”模板；
- 提供模板 ID、字段名、字段类型和示例值。

阶段 C 前：

- 在“丽人服务”类目模板库中查找符合实际场景的“新咨询提醒”或“新留言提醒”；
- 如无可用模板，提交模板申请；
- 模板审核前可以完成站内聚合和前台提醒，但不能宣称离线聊天通知已完成。

阶段 D 前：

- 准备一台 iPhone 和一台 Android 真机；
- 准备可进入 `pending_shop` 的未来预约。

## 9. 测试清单

后端自动化测试：

- 授权次数累计、拒绝、禁止和成功消费；
- 并发消费只允许一个任务取得授权；
- 微信失败、重试和事件去重；
- 预约状态转换的收件人和模板选择；
- 聊天未读聚合、已读停止升级；
- 上海时区、跨日预约和重复定时任务。

小程序检查：

- 首页和提醒保障页三种状态；
- 授权弹窗只能由用户点击触发；
- 前台横幅、震动节流和跳转；
- 每日摘要的正常、空、失败和新增事件状态；
- 日历权限拒绝、重新授权、重复同步和预约改期；
- 长客户名、长项目名、窄屏和底部安全区。

真机主链路：

1. 美甲师点击一次开启接单提醒；
2. 客户创建预约，美甲师收到微信服务通知；
3. 客户确认、拒绝、取消和改期，美甲师收到对应状态通知；
4. 客户连续发送多条消息，五分钟未读后只收到一条聚合提醒；
5. 美甲师正在使用小程序时，新消息触发横幅和一次短震动；
6. 已确认预约加入系统日历并在正确时间提醒；
7. 次日首次打开小程序时只展示仍未处理的摘要。

## 10. 推荐执行顺序

按 `A → B → C → D → E` 执行。A、B 优先保障预约变化；C 尽量补足客户消息触达；D 解决已经确认预约仍可能遗忘的问题。

如果微信模板库无法提供咨询/留言模板，则阶段 C 仍完成站内聚合、前台横幅、震动和每日摘要，但离线聊天提醒只能作为明确的产品限制保留，不能使用预约模板绕过平台规则。
